Time-Travel Portfolio Backend

How the Python pipeline turns ten years of market prices into thirty backtests (six investors under five portfolio methods), and how the demo site replays and compares them in your browser.

How to read this

This page explains the whole backend in one sitting, from the first download of prices to the moment a number appears on the site. It assumes you can read Python but does not assume you know anything about investing or optimisation. Every term is defined the first time it is used, in a box like the one below, and the glossary at the end collects all of them.

Backend

The part of a software project that prepares data and does the computation, as opposed to the part the user looks at. Here the backend is a set of Python scripts that run once, on a laptop, and write files. The site then only reads those files.

Each section makes one main point, gives one example, and sometimes ends with a short question so you can check that the point landed. Where a concept is deeper than this page can go, a grey box lists a good source or a search phrase for YouTube. Amber boxes record mistakes that were made along the way and what they taught.

The whole picture

The project has two halves that never run at the same time. The Python half downloads prices, builds mathematical models, and replays ten years of decisions for six imaginary investors under five different methods. It writes its answers as JSON files into the site's static/data folder. The site half is a static web page that fetches those files and draws them. There is no server, no database, and nothing is computed on demand except the user's own buy-and-hold picks, which are cheap enough to simulate in the browser.

JSON (JavaScript Object Notation)

A plain-text file format for lists and key–value records, for example {"cagr": 0.107, "sharpe": 0.70}. Python writes it with json.dumps and the browser reads it with response.json(), so it is the natural handover format between the two halves.

The order in which things run is fixed. First data.py builds the cleaned price tables. Then tune.py may be run to pick defaults using only 2011–2015. Then export.py runs one backtest per investor per model over 2016–2025 and writes the JSON. Finally the site is built. The sections below follow that order, module by module, and then cross into the site.

The words you need first

Four ideas come up in every module, so they are worth fixing before reading any code: a price, a return, a weight, and a portfolio.

Stock, ticker, ETF

A stock (or share) is a small slice of ownership of a company that can be bought and sold on an exchange. A ticker is the short code the exchange uses for it, such as AAPL for Apple. An ETF (Exchange-Traded Fund) is a bundle of many investments that trades like a single stock; this project uses AGG, which holds thousands of US bonds, GLD, which holds gold, and SPY, which holds the 500 largest US companies.

Price and daily return

The price is what one share cost at the close of a trading day. The daily return is the fractional change from one close to the next: if a share closes at $100 on Monday and $102 on Tuesday, Tuesday's return is 102/100 − 1 = 0.02, or 2%. The whole pipeline works in returns rather than prices, because returns can be compared across assets with very different price levels.

Portfolio and weight

A portfolio is the set of everything you hold. A weight is the fraction of your total money in one asset. If you have $10,000 and $1,200 of it is in Apple, Apple's weight is 0.12. Weights across the whole portfolio always add to 1. Every model's entire job is to choose weights.

Benchmark and S&P 500

A benchmark is the simple alternative you compare a strategy against. Here it is buying SPY once and never touching it. SPY tracks the S&P 500, an index of roughly the 500 largest US companies weighted by size, which is the usual stand-in for "the US stock market".

One worked example ties these together. Suppose on 4 January 2016 a portfolio holds weights of 0.5 in Apple and 0.5 in cash, and the next day Apple returns −2% while cash returns 0%. The portfolio's return that day is 0.5 × (−0.02) + 0.5 × 0 = −0.01, a 1% loss. That single formula, "portfolio return equals the weighted sum of asset returns", is what every model file and the backtest loop are built on.

Check yourself. If the portfolio above loses 1% on that day, what are its new weights? (They are no longer 0.5 and 0.5, and that drift is why the backtest has a "drift trigger".)

Running it yourself

The Python side is a package called portfolio living in src/portfolio, managed with uv. The site is a Node project in site/. The only one-off setup step is activating the AMPL licence, which you must do yourself because the licence is personal.

uv

A fast Python package and environment manager. uv run makes sure the virtual environment in .venv matches pyproject.toml and uv.lock, then runs the command inside it, so you never activate an environment by hand.

# one-time: AMPL for Academics licence (your own UUID). It is stored inside .venv,
# so repeat this if .venv is ever recreated. The current licence expires 24 Sept 2026.
uv run python -m amplpy.modules activate <uuid>

# 1. download prices and build data/processed/*.parquet (cached in data/raw/)
uv run python -m portfolio.data

# 2. run the tests (needs step 1 and a working licence)
uv run pytest

# 3. optional: hyperparameter grid on 2011-2015 for two profiles
uv run python -m portfolio.tune builder preserver

# 4. backtest every profile under every model and write site/static/data/
uv run python -m portfolio.export                      # 30 runs, 4 in parallel, ~4 minutes
uv run python -m portfolio.export --model robust       # only one model (repeatable flag)
uv run python -m portfolio.export --profile sprinter --jobs 1   # one profile, serial

# 5. the site (Node 22, see site/.nvmrc)
cd site && npm install && npm run dev       # http://localhost:5173
npm run build                              # static output in site/build/

The dependencies in pyproject.toml are yfinance and pandas-datareader for downloading, pandas, numpy and pyarrow for tables, and amplpy with three solver modules from AMPL's own package index: ampl-module-base, ampl-module-highs and ampl-module-gurobi. quantstats is installed but unused; the metrics were written by hand in metrics.py so the site could mirror them exactly.

universe.py — what the models may hold

src/portfolio/universe.py

This module is a frozen list, not a computation. It names 51 stocks, two ETFs, and one synthetic cash asset, and records the sector of each. Everything else in the pipeline imports these lists so that "the universe" is defined in exactly one place.

Universe

The set of assets an optimiser is allowed to choose from. A model can only pick from what you give it, so the universe is the first and most consequential design choice.

Sector (GICS)

An industry grouping. GICS (Global Industry Classification Standard) is the scheme used by S&P that puts every listed company into one of about eleven sectors, such as Information Technology or Utilities. Sectors matter here because one of the shared constraints caps how much can sit in any single sector, and because the site's Archive walks the user through the universe one sector at a time.

The selection rule

The docstring at the top of the file states the rule, applied once by hand and not revised since. A stock had to be in the S&P 500 on 1 January 2016; within each sector the largest companies by market value at the end of 2015 were taken, four to six per sector; and every stock needed a full daily price history back to April 2008, because the tuning period and the three-year estimation window both reach that far back. That last rule excluded Facebook (listed 2012) and LyondellBasell (listed 2010), and Oracle and PPG took their places.

Two extra assets give the models somewhere safe to go when stocks look risky: AGG (a broad US bond ETF) and GLD (gold). A third, CASH, does not exist on any exchange; it is manufactured in data.py from the interest rate on short-term US government debt.

Bond, T-bill, risk-free rate

A bond is a loan to a government or company that pays interest and returns the principal at a fixed date. A T-bill (Treasury bill) is a US government bond that matures within a year; the three-month T-bill is treated by convention as the closest thing to a risk-free investment, and its yield is called the risk-free rate. "Cash" in this project means money parked at that rate, not banknotes in a drawer.

Survivorship bias, disclosed

Companies whose tickers did not survive to 2026 (Dow/DuPont, Monsanto, Praxair and others) were skipped because yfinance cannot return their history. That means the universe is slightly tilted towards companies that turned out fine, which flatters every strategy that draws from it; the S&P 500 comparison is affected less, since SPY itself contains the failures. The file says this plainly and so should any presentation of the results.

Survivorship bias

The distortion that comes from studying only the things that survived. If you test a strategy on the companies that still exist today, you have quietly removed every bankruptcy from the sample.

data.py — fetching and cleaning prices

src/portfolio/data.py

This module downloads daily prices once, caches them, and produces four aligned tables that every later stage reads. Its one rule is that it only stores history; deciding what a model is allowed to see on a given date is somebody else's job (estimate.py).

Downloading

fetch_prices loops over the 53 tickers plus SPY. For each it looks for data/raw/<ticker>.parquet; if the file exists it is read, otherwise yfinance downloads the full history from 1 April 2008 and the file is written. Passing refresh=True forces a re-download. data/raw is git-ignored, so a fresh clone downloads everything on the first run.

Parquet

A compact binary file format for tables, read and written by pandas through pyarrow. It is much faster and smaller than CSV and preserves column types, which is why every table in data/ uses it.

Adjusted close (auto_adjust=True)

Two things break a naive price series. A dividend is cash a company pays to shareholders, and on the day it is paid the price drops by about that amount even though the holder lost nothing. A stock split replaces every share with, say, four shares at a quarter of the price. The adjusted close rewrites past prices so that both effects disappear, and the return series then measures what an investor who reinvested dividends actually earned. yfinance does this when auto_adjust=True.

Manufacturing CASH

fetch_tbill pulls the daily three-month T-bill yield (FRED series DTB3, an annual percentage) and falls back to Yahoo's ^IRX if FRED is unreachable. In build_dataset that annual yield is turned into a daily return and compounded into a price-like series that starts at 1:

daily_rf = (1 + tbill / 100) ** (1 / 252) - 1     # annual % → daily fraction
close["CASH"] = (1 + daily_rf).cumprod()           # a "price" that grows at that rate

The number 252 is the usual count of US trading days in a year and is used for every annualisation in the project. The result is that CASH behaves like any other column: it has a price, it has a daily return, and a model can hold it with a weight.

Alignment and the four outputs

Different tickers occasionally have different trading days in the raw download (a few odd half-days). close.dropna(how="any") keeps only dates where every ticker traded, which removes a handful of rows and guarantees that every table has identical dates. Then the module writes:

estimate.py — what a model is allowed to see

src/portfolio/estimate.py

This module is the honesty gate of the project. Its first function decides which days of history a decision may use, and it always stops strictly before the decision date. The other functions turn that history into the inputs the models need: an expected return per asset, a covariance matrix for the mean-variance models, a conversion between the two risk languages, and the realised CVaR of a set of weights.

Look-ahead bias

Accidentally letting a simulated decision use information that did not exist yet, for example fitting a model on 2016–2025 and then "testing" it on 2016–2025. It is the single most common way backtests lie, and it is prevented here by construction rather than by care.

window_before

def window_before(returns, t, lookback_days):
    hist = returns.loc[: t - pd.Timedelta(days=1)]   # everything before t, never t itself
    if len(hist) < lookback_days: raise ValueError(...)
    return hist.iloc[-lookback_days:][ASSETS]

Given a date t and a lookback, it returns the last lookback_days rows of returns dated before t. The default lookback is 756 trading days, three years. Because the returns table starts in April 2008, the earliest date this can serve with a 756-day window is April 2011, which is exactly where the tuning period begins.

expected_returns — a shrunk average

The simplest estimate of what an asset will return tomorrow is the average of what it returned over the window. That average is famously noisy: over three years the ranking of assets by sample mean is mostly luck, and an optimiser will happily pile into whatever was lucky. The standard cheap fix is shrinkage: pull every asset's estimate part-way towards the average across all assets.

m = scenarios.mean()                       # sample mean per asset
risky = m.drop("CASH")
out = (1 - shrink) * risky + shrink * risky.mean()
out["CASH"] = m["CASH"]                     # cash is not a noisy estimate; leave it alone

With shrink = 0 each asset keeps its own average; with shrink = 1 every risky asset gets the same expected return and a model can only distinguish them by risk. The tuned value is 0.75. Worked example: if Apple's three-year daily mean is 0.0012 and the cross-asset mean is 0.0004, the shrunk estimate is 0.25 × 0.0012 + 0.75 × 0.0004 = 0.0006. All five models receive the same shrunk mu, so they differ only in how they treat risk.

Lesson learned: never shrink cash

An early version shrank CASH along with the stocks. Cash's true expected return (the T-bill rate, near zero for most of the decade) got pulled up towards the stock average, so the model thought cash paid like a stock without any risk, and sat in cash. Cash's mean is not an estimate at all, it is the known rate, so it is now exempt. The same exemption applies to the covariance below.

covariance and ledoit_wolf

Covariance matrix (Σ)

A table with one row and one column per asset. The diagonal entries are each asset's variance, the square of its volatility; the off-diagonal entries say how much two assets move together. With weights w, the portfolio's variance is wᵀΣw, which is the quantity the Markowitz models cap.

covariance(scenarios, method) builds Σ over the window for the 53 risky assets and then embeds it in a 54 × 54 matrix whose CASH row and column are zero, because cash's variance is known to be almost nothing. With method="sample" it is the plain population covariance. With method="ledoit_wolf" it is shrunk:

Ledoit–Wolf shrinkage

A 53 × 53 covariance has 1,431 distinct numbers estimated from 756 days, so it is noisy in a specific way: the largest eigenvalues are too large and the smallest too small, and an optimiser exploits exactly those errors. Ledoit and Wolf (2004) pull the sample matrix part-way towards a simple target, a scaled identity (every asset given the same variance, no correlation), with an intensity computed from the data itself rather than chosen by hand. ledoit_wolf(x) implements their formula in about fifteen lines of NumPy and returns both the matrix and the intensity; on the 2016 window the intensity is a few percent.

cvar_to_vol — translating the investor's promise

Every investor profile states its risk appetite as a CVaR limit (next section), but the mean-variance models only understand variance. cvar_to_vol converts one to the other under the assumption that daily returns are normally distributed with zero mean:

CVaR_α = σ · φ(z_α) / (1 − α) → at α = 0.95, CVaR ≈ 2.063 · σ

So a 2.0% daily CVaR limit becomes a daily volatility cap of about 0.97%, and the models square it to get a variance cap. The normal assumption is an approximation: real returns have fatter tails than a bell curve, so a portfolio that meets the volatility cap tends to show a realised CVaR a little above the original limit (the Builder's Markowitz runs show 2.0% against a 2.0%→1.0% glide path where the CVaR model shows 1.9%). That gap is one of the things the lab makes visible.

realised_cvar

The last function computes, for a given set of weights, the average loss over the worst 5% of scenario days. It is used after every solve, for every model, so that the solve log carries one risk number that is comparable across methods regardless of which measure the model itself optimised.

Measuring risk: VaR and CVaR

Every investor archetype in this project is defined mainly by one number: the largest average loss they will accept on their bad days. That number is a CVaR limit. To read the models you need to understand what CVaR measures and the trick that lets a linear solver compute it.

Scenario

One possible outcome for tomorrow. This project takes each of the last 756 days of history as one scenario, all equally likely: "tomorrow could look like any of these days". The CVaR model never assumes a bell curve or any other formula for returns; it just uses the days that happened.

VaR (Value at Risk)

The loss you would exceed only on the worst (1 − α) share of days, for a chosen confidence level α. With α = 0.95 and 756 scenarios, sort the daily losses from worst to best; the 95% VaR is the loss at the boundary of the worst 5%, that is roughly the 38th-worst day. VaR answers "how bad is a bad day?" but says nothing about how bad the days beyond it are.

CVaR (Conditional Value at Risk), also called Expected Shortfall

The average loss over those worst 5% of days. It is always at least the VaR, and it does account for how deep the tail goes. A daily 95% CVaR of 2% means "on your 5% worst days you lose 2% on average". As a rough feel, a portfolio with a daily CVaR of 2% loses about 8–10% in a bad month.

A miniature example with twenty scenarios and α = 0.95 makes the difference concrete. The worst 5% of twenty days is one day. Suppose the two worst daily losses are 6% and 3%. The VaR is the boundary of the worst 5%, so it is about 6% (with one day in the tail, VaR and CVaR coincide). Now suppose there were forty days, so the tail holds two days: VaR is 3% (the boundary), and CVaR is the average of 6% and 3%, which is 4.5%. CVaR noticed the 6% day; VaR did not.

The Rockafellar–Uryasev trick

Computing "the average of the worst 5%" seems to need sorting, which is not something a linear program can do. Rockafellar and Uryasev (2000) showed that CVaR is the minimum over a free number ζ (zeta) of the following expression, where L_s is the portfolio loss in scenario s and [x]⁺ means "x if positive, else 0":

CVaR_α = min over ζ of: ζ + (1 / ((1 − α) · nS)) · Σ_s [L_s − ζ]⁺

The intuition is that ζ is a threshold you are guessing, and you pay for every scenario whose loss overshoots it, scaled up by 1/(1 − α) so that overshoots count 20 times. The expression is smallest exactly when ζ equals the VaR, and at that point its value equals the CVaR. In a model you replace [L_s − ζ]⁺ with a new non-negative variable u_s and a constraint u_s ≥ L_s − ζ; because the objective pushes every u_s as low as it can go, the two are equivalent and everything stays linear. That is precisely what cvar.mod does with its zeta, u[s], and tail_loss constraint.

Linear program (LP)

An optimisation problem in which the objective and every constraint are straight-line (linear) functions of the decision variables. LPs with hundreds of thousands of variables solve in seconds with standard software, which is why a linearisable risk measure like CVaR is so useful.

model/common.mod — the investor's rules

model/common.mod, loaded before any of cvar.mod, markowitz.mod, robust.mod

Every optimising model shares the same investor rules, so those rules live in one AMPL file that is read first; a second, short file then adds the risk measure and the objective. The split is what makes "the same investor under different methods" a true statement: the constraints are literally the same text.

AMPL and solvers

AMPL (A Mathematical Programming Language) is a language for writing optimisation models in something close to mathematical notation, separately from the data. A solver is the program that actually finds the best solution. This project uses two: HiGHS, free and open-source, for linear and mixed-integer linear problems, and Gurobi, a commercial solver available under the academic licence, for problems with quadratic terms. amplpy is the Python library that loads a model, fills in its data, and calls whichever solver is named; switching solver is one line and the model files do not change.

MILP (Mixed-Integer Linear Program)

A linear program in which some variables must be whole numbers, here 0 or 1. Integer variables let a model express yes/no decisions ("do I hold this asset at all?"), at the cost of making the problem much harder in theory. In practice, this one has 53 binaries and HiGHS solves it in a fifth of a second.

Basis point (bp)

One hundredth of one percent. A 10 bp cost means paying $1 for every $1,000 traded, a reasonable all-in figure for large US stocks including the gap between buying and selling prices.

Decision variables and shared expressions

var w    {a in ASSETS} >= 0, <= w_max[a];   # the weights: the actual decision
var z    {ASSETS} binary;                   # 1 if the asset is held at all
var buy  {ASSETS} >= 0;                     # how much weight is bought ...

var turnover   = sum {a in ASSETS} (buy[a] + sell[a]);    # total weight that changes hands

Cardinality constraint

A limit on how many things are chosen, as opposed to how much. "Hold at most twelve stocks" is a cardinality constraint. It cannot be written with weights alone, because a weight of 0.0001 would still count as not holding, so a binary indicator per asset is needed.

Worked example of the link constraints: with w_max = 0.12 and w_min_pos = 0.02, asset a may have weight 0 (with z = 0) or any weight in [0.02, 0.12] (with z = 1), but nothing in between 0 and 0.02. The binaries make the feasible region disconnected, which is exactly what a plain LP cannot represent.

CVaR limit (the project's own)

model/cvar.mod · src/portfolio/models/cvar.py

The file adds the scenario set and returns r[s,a], the confidence level alpha and the investor's cvar_limit, the Rockafellar–Uryasev variables zeta and u[s], and two constraints:

var cvar = zeta + sum {s in SCENARIOS} u[s] / ((1 - alpha) * nS);

maximize objective:  hold_days * exp_return - lambda_risk * cvar - cost_rate * turnover;

subject to tail_loss {s in SCENARIOS}:  u[s] >= -sum {a in ASSETS} r[s,a] * w[a] - zeta;
subject to loss_tolerance:              cvar <= cvar_limit;

The objective wants the highest expected return over the holding period, minus what it costs to get there; risk is a hard limit rather than a penalty, which is why lambda_risk is zero for every profile.

Lesson learned: scale return by hold_days

The first version maximised exp_return − cost_rate · turnover. Expected return is a daily number, around 0.0005, while switching a 10% position costs 0.001 × 0.2 = 0.0002 once. One day of return could never justify a trade, so the model sat in cash and never rebalanced. Multiplying the return by the 21 days the position is expected to be held compares like with like. Every model's objective now has the same hold_days factor.

Markowitz, two ways

model/markowitz.mod · src/portfolio/models/markowitz.py

Markowitz mean-variance optimisation

The 1952 idea that started portfolio theory: describe each portfolio by two numbers, its expected return and its variance, and choose the highest return for a given variance. Its inputs are a vector of expected returns and a covariance matrix; its weakness is that it trusts both completely, and both are noisy.

The file adds Sigma and a cap var_limit, and replaces the CVaR constraint with a quadratic one:

var variance = sum {i in ASSETS, j in ASSETS} w[i] * Sigma[i,j] * w[j];

maximize objective:  hold_days * exp_return - lambda_risk * variance - cost_rate * turnover;
subject to risk_tolerance:  variance <= var_limit;

var_limit is the investor's CVaR limit on that day passed through cvar_to_vol and squared, so the glide path applies here too. The two variants are one class, MarkowitzModel(cov_method), differing only in whether covariance() is asked for the sample or the Ledoit–Wolf matrix. A quadratic constraint together with the binaries makes this a MIQCP (Mixed-Integer Quadratically Constrained Program), which HiGHS cannot solve and Gurobi solves in well under a second.

Lesson learned: solver tolerances have units

Daily variances are around 5 × 10⁻⁵. Gurobi's default feasibility tolerance is 10⁻⁶, which sounds tiny but is 2% of that constraint, and the first test run showed the variance cap exceeded by exactly that much. The fix is to hand the solver covariances in percent² (multiplied by SCALE2 = 10⁴ in models/base.py) so a typical variance is 0.5 and the tolerance is negligible, and to tighten feastol to 10⁻⁸. Python converts back before reporting. The AMPL files say which units they expect in their comments.

Robust mean-variance

model/robust.mod · src/portfolio/models/robust.py

Robust optimisation

Instead of trusting an estimate, assume the true value lies somewhere in a set around it and optimise for the worst case in that set. Here the uncertain quantity is the vector of expected returns mu, and the set is an ellipsoid whose shape comes from how uncertain each estimate is.

Standard error

How far a sample average is likely to be from the true average. For a mean of n daily returns with standard deviation σ, it is σ / √n. With 756 days and a typical stock's σ of 1.2% a day, the standard error is about 0.044% a day, which is roughly the size of a stock's whole expected excess return. That single fact drives everything about this model.

The covariance of the estimation error is Omega = Sigma / n. For a long-only portfolio the worst-case expected return over an ellipsoid of radius kappa standard errors has a closed form, mu·w − kappa · √(wᵀ Omega w), and the square root is handled by a cone variable:

var t >= 0;                                              # t >= sqrt(w' Omega w)
var worst_return = exp_return - kappa * t / sigma_scale;  # Omega is in percent^2, so t is a percent

maximize objective:  hold_days * worst_return - lambda_risk * variance - cost_rate * turnover;
subject to cone:            sum {i,j} w[i] * Omega[i,j] * w[j] <= t * t;
subject to risk_tolerance:  variance <= var_limit;

The same variance cap as Markowitz applies, so the only difference between robust and markowitz_lw is the kappa · t haircut on expected return. This is a MISOCP (Mixed-Integer Second-Order Cone Program), which Gurobi handles; it is the slowest model, occasionally reaching the two-minute time limit, in which case the best solution found so far is used (see optimiser.py).

Lesson learned: units, again

When the covariance scaling above was introduced, t silently became a percent while exp_return stayed a fraction, so the haircut was 100 times too large and every robust run sat in cash for ten years. The export log made it obvious (a 2.2% CAGR with zero drawdown is a cash account), and sigma_scale in the model file is the fix. The general rule: any time a model mixes two quantities, write down the units of both.

How big should kappa be? That is a hyperparameter, so it was checked on 2011–2015 like the others; the result is in the tuning section and is the reason the default is the conventional 1.0 rather than a tuned value.

Equal weight (1/N)

src/portfolio/models/equal.py

Put the same weight in every allowed non-cash asset and rebalance back to equal whenever a trigger fires. There are no estimates and no solver; the class computes the weights in three lines and reports the turnover against the previous weights. It ignores every investor rule except exclusions, so the Ethical Investor's 1/N portfolio still holds no oil company and no Philip Morris. It is here because a well-known paper (DeMiguel, Garlappi and Uppal, 2009) found that no optimised strategy consistently beat 1/N out of sample; this project's results agree on return and disagree on risk.

def ampl_solve(model_file, solver, sets, params, values=()):
    ampl = _get_ampl()                       # one AMPL session per process, reused
    ampl.reset(); ampl.read(COMMON); ampl.read(model_file)
    ...fill sets and params...
    ampl.solve()
    if ampl.solve_result not in ("solved", "limit"): raise RuntimeError(...)
    return weights, {v: ampl.get_value(v) for v in values}, status, seconds

MIP gap

A solver proves a mixed-integer solution is optimal by squeezing an upper bound and the best solution found towards each other. The relative gap is how far apart they still are; stopping at 0.01% (HiGHS) or 0.1% (Gurobi) means the returned answer is within that fraction of the best possible, far below the noise in the inputs.

Three details matter. Creating an AMPL session starts a separate process and is slow, so _get_ampl keeps one per Python process and each solve only pays for reloading the model text. A result of "limit" (the solver stopped on its time limit but has a feasible solution) is accepted and recorded in the solve log's status, because a slightly sub-optimal robust portfolio is preferable to an aborted backtest; anything else, such as "infeasible", raises an error and stops the run. And Gurobi is told to use two threads, because export.py runs four backtests at once and four unrestricted Gurobis on one laptop starve each other into time limits.

profiles.py — six investors as numbers

src/portfolio/profiles.py

A Profile holds what a person would tell an adviser: how long the money is for, how much loss they can stomach, how many holdings they want, and any exclusions. params_at(years_left) translates that into the parameter dictionary every model receives on a given date. Only one thing changes with time: the loss limit.

The glide path

Horizon and glide path

The horizon is how many years until the investor needs the money. A glide path is a rule that makes a portfolio safer as the horizon shrinks, the idea behind "target-date" retirement funds. Here it is a straight line on the CVaR limit:

cvar_limit(years_left) = cvar_end + (years_left / horizon_years) · (cvar_start − cvar_end)

For The Builder, cvar_start = 0.020 and cvar_end = 0.010 over ten years, so at the start a model may run a 2.0% daily CVaR, five years in 1.5%, and in the final months only 1.0%. The mean-variance models see the same path after translation to a volatility cap. This is the project's first "policy" idea: the risk budget is a state that depends on time, not a constant.

backtest.py — replaying ten years honestly

src/portfolio/backtest.py

A backtest replays a strategy day by day over history as if it had been run live. This one walks forward through every trading day from 4 January 2016, lets the portfolio earn that day's returns, decides whether to re-solve, and if so asks the model for new weights using only history before that day and trades at that day's close. The whole module is one loop and the honesty lives in its ordering. The signature is run_backtest(profile, data, model="cvar", start, end, initial=100_000); model may be a key or a Model object.

Walk-forward backtest

A simulation that moves through time in order, making each decision with only the data that was available at that moment, then revealing the next day and repeating. It is the opposite of fitting one model to the whole period at once.

Rebalance

Trading a portfolio back to a chosen set of weights. Weights drift on their own as prices move, so any strategy that targets weights has to decide when to rebalance and pay the trading costs of doing so.

One day in the loop

Let holdings be a Series of dollar amounts per asset, starting as all cash. For each trading day t:

  1. Earn. Except on the very first day, multiply each holding by 1 + returns.loc[t]. Compute the new total and the current weights w = holdings / total.

  2. Decide whether to re-solve. A reason is set if any trigger fires (next subsection). On the first day the reason is "start".

  3. Re-solve, if needed. Compute years_left to the horizon end. Take the 756-day window before t, shrink its means, ask the profile for its parameters at this years_left, and call model.solve(scen, mu, params, w_prev=w).

  4. Trade and pay. The new dollar holdings are weights × total. The amount traded is the sum of absolute dollar changes; the cost is cost_rate times that; and the cost is taken out of every position pro rata by scaling all holdings by 1 − cost/total. Every asset whose weight changed by more than 0.01 percentage points is logged as a trade, and one row is logged for the solve itself, including the model's own risk number and the comparable cvar.

  5. Record. Append today's total value and weights.

The new weights earn returns only from t + 1. So a model never earns a return on the same day's data it was allowed to see, and the scenarios it saw ended the day before t. Worked example from the exported Builder × CVaR run: on 4 January 2016 the first solve moved 98% of $100,000 out of cash into nine holdings, so turnover was 1.96 (buys plus sells), the cost was 0.001 × 1.96 × 100,000 = $196, and the recorded value on day one is $99,804. That is why the site's adviser line starts a hair below the S&P line.

The triggers

This is the project's second "policy" idea: rebalancing is event-driven rather than on a fixed calendar, and the same policy is applied to all five models so that they differ only in what they decide, not in when. After a cooldown of min_days_between (10 trading days, so a crash cannot cause a solve every day), the loop checks three conditions in this order and uses the first that fires:

ReasonConditionWhy it exists
calendar63 trading days (one quarter) since the last solveA floor on attention: even a quiet market gets a review each quarter and the glide path keeps tightening.
driftΣ |w − target| ≥ 0.10, where target is the last solved weightsPrices have pulled the portfolio 10 percentage points in total away from what was chosen.
volatility21-day volatility of the equal-weight universe ÷ its 252-day volatility ≥ 2.0The market has become twice as jumpy as usual, so the risk the old weights carry has changed even if the weights have not.

Volatility

The standard deviation of returns, that is how widely they scatter around their average. High volatility means big moves in both directions. market_vol_ratio computes it over the last 21 and 252 trading days on the average return of all 53 tickers, again using only data before t.

In the exported Builder × CVaR run there were 49 solves: 1 start, 34 calendar, 5 drift, and 9 volatility. The volatility trigger fired in February–March 2018, March–April 2020 and April–May 2025, which is what it is for.

The benchmark and the horizon

The benchmark is SPY bought once with the same initial amount; its series is normalised so that day one equals initial, matching the portfolio's day one, on which no return is earned. The end date is the earlier of the requested end and start + horizon_years, so The Sprinter's backtests run only three years, to 4 January 2019, with 757 days instead of 2,514, and its benchmark metrics cover the same three years.

The function returns a BacktestResult with the profile, the model, the daily value series, daily weights, the benchmark series, the solve log, the trade log, and the metrics of both portfolio and benchmark.

tune.py and the kappa grid — choosing defaults without peeking

src/portfolio/tune.py · data/processed/tuning.json · data/processed/tuning_robust.json

Some settings are not part of any investor's story but still affect results: the lookback window, the shrinkage, the drift trigger, the volatility trigger, and the robust model's kappa. They are hyperparameters, and choosing them by trying values on 2016–2025 would be look-ahead bias in another disguise. So they were tried on 1 April 2011 to 31 December 2015, a period the site never shows.

Hyperparameter

A setting of the method itself rather than a quantity the method estimates. A model estimates expected returns; how many days of history to estimate them from is a hyperparameter.

The grid and the selection rule

GRID = {
    "lookback_days": [504, 756],          # two or three years of scenarios
    "shrink":        [0.5, 0.75, 1.0],
    "drift_trigger": [0.10, 0.20],
    "vol_trigger":   [1.5, 2.0, 99.0],    # 99 = volatility trigger effectively off
}

That is 36 combinations, run for The Builder and The Preserver under the CVaR model, so 72 backtests in a process pool of four. For each run it records CAGR, Sharpe, maximum drawdown, realised CVaR, the profile's average CVaR limit over the run, their ratio, and total turnover. The selection rule is stated in the docstring: keep configurations whose realised CVaR stayed within 10% of the average limit (the risk promise was kept), then take the highest Sharpe, with ties going to the one that traded least.

What it found, and what was actually chosen

The per-profile winners disagreed on shrinkage and drift (Builder's best was shrink 0.5 and drift 0.2; Preserver's was shrink 0.75, drift 0.1, and no volatility trigger). Rather than give each profile its own tuned settings, which would overfit two small samples, the defaults in profiles.py were set from the marginal means of Sharpe across all 72 runs, that is the average Sharpe of every run that used a given value:

  • test_ledoit_wolf_is_valid_covariance: the shrinkage intensity lies strictly between 0 and 1, the matrix is symmetric and positive definite, and CASH's row and column are zero.

  • test_solution_respects_constraints, run for each of the four optimising models: weights sum to 1, no asset exceeds its 10% cap, every held asset is at least 2%, at most 15 are held, the excluded ticker (PM) is absent, the Energy sector stays within its 5% cap, and the model's own risk measure is within its limit.

  • test_tighter_limit_means_less_risk_and_return, for each optimising model: a 1.0% limit produces no more risk and no more expected return than a 2.0% limit. This checks the economic direction of each model, not just its feasibility.

  • test_equal_weight_ignores_everything_but_exclusions: 52 equal weights, no cash, no PM, turnover of exactly 2 from all-cash.

  • test_robust_is_more_cautious_than_markowitz: with the same inputs the robust model's expected return is no higher than Markowitz + Ledoit-Wolf's.

Into the site

Everything from here on happens in the browser. The site is written in SvelteKit with hand-written CSS, D3 for the charts, and Three.js for the timeline. This section follows the same data through the site that the earlier sections produced, so you can trace any number on screen back to a line of Python.

SvelteKit, Svelte 5 runes

Svelte is a framework for building web interfaces from components, files that mix HTML, JavaScript and CSS. SvelteKit adds routing and building around it. Svelte 5 introduced runes, functions like $state and $derived that mark which values are reactive, meaning the page redraws automatically when they change.

A site with no server

vite.config.ts uses adapter-static and +layout.ts sets prerender = true. That means npm run build produces a folder of plain HTML, JavaScript and JSON in site/build that any file host can serve; there is no code running on a server after deployment. Everything in site/static, including data/, is copied into the build unchanged, so a URL like /data/runs/builder__cvar.json simply returns the file export.py wrote. Deployment is a push to GitHub that Vercel builds and hosts.

Static site

A website whose files are fixed at build time and served as-is. It cannot compute anything per visitor on the server, which is exactly why the heavy work was precomputed as a grid. The trade-off is that a user can only explore combinations that were exported; a new risk limit or a sixth model needs a Python run and a redeploy.

data.ts — loading and typing the JSON

site/src/lib/data.ts

This file declares a TypeScript interface for each JSON file (Universe, Prices, RunIndex, RunResult, Archive, Notes2015, MarketEvent, and the pieces they contain), and every field name in them matches the Python dictionary keys exactly. If a key is renamed in export.py, the type here must change too; there is no runtime check. The loaders are one line each:

Rewind is the 3D timeline. Its only use of backend data is decorative but real: it computes a 21-day rolling volatility of SPY from prices.json, maps it to a 0–1 "roughness" along the track, and uses that to make the glowing thread thicker and rougher in turbulent periods like March 2020. Three motion details are worth knowing because they were deliberately reworked. The opening flight starts far along the thread's future extension (the thread is drawn 4,200 units past 2026 for this purpose), with the camera riding just above the fibres and looking along them, already at full speed; it eases out to a stop exactly at 2026 and only then swings out to the side view. For the first third of the flight the camera looks far down the thread, so the fibres converge on the centre of the screen, which is where the star streaks converge too. An afterimage pass (Three.js's AfterimagePass) provides motion blur whose trail length follows the camera's speed, so the streaks dissolve as the camera slows. And the handoff from the prologue's star warp is continuous: the starfield is one canvas owned by +page.svelte that spans both stages, the warp never burns to black, the stage switches without the fade curtain, the timeline's canvas fades in underneath the still-streaking stars once its first frame has rendered, and the stars fade out over two seconds and are then unmounted. The flight's clock starts at that first rendered frame, not at page load, so a slow load of the 3D module never eats the start of the flight. The arrival branch is built relative to the thread's centre line at 1 January 2016 (not the world origin, which sits about 23 units off the thread), and pressing Arrive first scrolls the traveller exactly to that point, so the branch peels out of the traveller itself. The portals (the circular views into each event) are DOM elements pinned to the 3D scene, and their layout is done in screen space from measured sizes rather than in world space from constants. Every frame the renderer projects the thread's own point for each event to the screen, then places the portal at a lane offset (a fraction of the viewport height, 24% for the near lane and 42% for the far) clamped so that the whole measured box, the lens plus the caption on whichever side it stacks, stays inside the viewport with a margin; caption heights are measured live with bind:clientHeight, so a blurb opening or text wrapping differently on a phone is accounted for. The chosen screen point is unprojected back to world space at the thread's depth and the event's branch, a unit-length geometry in its own object, is rotated and scaled to land its tip there, so the 3D branch follows the portal and perspective, sway and the camera's angle drop out of the problem. Sideways, portals scroll in and out as the timeline moves and are fully faded by the time the lens touches an edge; while a lens is on screen its caption slides sideways (near lane) or flips to the other side of the lens (far lane) to stay inside the viewport, and once the lens has left, the caption leaves with it rather than being held in frame. An event is not rendered at all unless its lens is at least partly on screen. The check is numeric: a sweep over every scroll position asserting that every on-screen lens and caption is inside the viewport and that no caption is shown whose lens is off screen, run at several window sizes.

Every other stage change goes through a short curtain: go() in state.svelte.ts darkens the screen for 450 ms, switches the stage, then lifts the curtain, coloured to match the world it is entering.

sim.ts and letters.ts — the browser's copy of the maths, and the prose

site/src/lib/sim.ts · site/src/lib/letters.ts

buyAndHold(prices, dollars, total) prices the user's picks on every day as Σ dollars[t] × normalised price[t] plus leftover cash growing with the CASH column. Because prices are normalised to 1.0 on day one, "$1,200 in Apple" is simply 1200 × row[AAPL]. There are no trading costs on the user's side, on the argument that one purchase in 2016 is negligible against ten years. summarise(dates, value, rf) is a line-by-line port of metrics.py; if you change a formula there, change it here too.

letters.ts turns each row of a run's solves into a short letter from the adviser: the opening sentence is chosen by the reason field, the three largest increases and decreases that day are named using company names from universe.json, the day's loss limit is stated in words with a note that it tightens as the horizon shrinks, and the trading cost closes the letter. It works for any model's run, which is what lets the simulator's letter panel read any adviser the user adds.

Rebuilding after a change

Because the two halves communicate only through files, the update path is always the same three steps, and skipping one is the usual cause of "the site shows old numbers":

  1. Change the Python (a profile number, a constraint, a model) and run uv run python -m portfolio.export, or with --profile / --model for a subset. This overwrites the JSON in site/static/data and merges the subset's rows into index.json.

  2. If a JSON key was added or renamed, update the matching interface in data.ts and whichever component uses it. If a model was added, nothing on the site needs to change: the lab reads the model list from index.json.

  3. Run npm run build in site/ (or let Vercel do it on push). The dev server on port 5173 picks up new static files without a rebuild; the preview server on 4173 does not.

What this does not do

A reader should leave knowing the edges as well as the mechanism.

  • Survivorship bias in the universe. Companies that disappeared before 2026 are missing, as described under universe.py.

  • Hand-picked archetype numbers. The six profiles' limits and caps are illustrative until the planned calibration from cited sources is done.

  • Scenarios are the past. The CVaR limit is enforced over the last three years of history, so a future that is worse than anything in the window will exceed the limit. The realised CVaRs show the size of that gap, and the mean-variance models add a second gap from the normal assumption in cvar_to_vol.

  • One rebalancing policy for all models. The drift and volatility triggers were tuned for the CVaR model and applied unchanged to the others so that the comparison isolates the decision rule. A fairer test of Markowitz might use its own tuned triggers.

  • Robust is not tuned. Its κ stays at the textbook value because tuning would have removed it; see the kappa grid.

  • No taxes, no slippage beyond 10 bp. Returns are total returns (dividends reinvested), costs are a flat proportional rate, and every trade fills at the closing price. The user's own buy-and-hold picks pay no cost at all.

  • The site cannot run new combinations. Only the exported grid exists; a custom risk limit or a sixth model needs a Python run and a redeploy.

  • The sentiment idea is not built. The stretch goal of feeding news sentiment into expected returns via Black–Litterman has no code yet.

Adjusted close

Backend
The offline Python pipeline that computes everything the site shows.

One hundredth of a percent.

The simple alternative a strategy is compared with; here, buying SPY and holding it.

A loan to a government or company; a T-bill is a US government loan of under a year.

Compound Annual Growth Rate: the constant yearly rate that reproduces the total growth.
Cardinality constraint
A limit on how many assets may be held, requiring binary variables.
Covariance matrix (Σ)
Per-asset variances on the diagonal and co-movements off it; wᵀΣw is portfolio variance.
CVaR / Expected Shortfall
The average loss over the worst (1 − α) share of scenarios.
Daily return
Today's price divided by yesterday's, minus one.
Drawdown
The fall from the highest value reached so far.
ETF
A fund holding many investments that trades like a single stock.
Glide path
A rule that lowers allowed risk as the horizon shrinks.
Gurobi
The commercial solver, under the academic licence, used for the quadratic and cone models.
HiGHS
The open-source solver used for the CVaR model.
Horizon
Years until the investor needs the money.
Hyperparameter
A setting of the method (lookback, shrinkage, triggers, κ), checked on 2011–2015.
JSON
The text format the Python side writes and the site reads.
Ledoit–Wolf shrinkage
Pulling a noisy sample covariance towards a scaled identity with a data-chosen intensity.
Look-ahead bias
Letting a simulated decision use information from its own future.
LP / MILP / MIQCP / MISOCP
A linear program; with integer variables; with a quadratic constraint; with a second-order cone constraint.
Markowitz mean-variance
Choosing weights for the best expected return at a given variance.
MIP gap
How far a mixed-integer solution may be from provably optimal when the solver stops.
Model (strategy pattern)
One of five interchangeable decision rules behind the same solve interface.
Parquet
A compact binary table format used for all cached data.
Portfolio / weight
Everything held; the fraction of money in each holding.
Rebalance
Trading back to chosen weights.
Risk-free rate
The T-bill yield; what "cash" earns here.
Robust optimisation
Optimising the worst case over a set of plausible inputs instead of a point estimate.

The reformulation that makes CVaR linear, using a threshold variable and one slack per scenario.

One backtest: one investor profile under one model, stored as runs/<profile>__<model>.json.

One historical day treated as a possible tomorrow.
Sector (GICS)
An industry grouping used for sector caps and the Archive's walk-through.

Return above cash per unit of volatility.

Pulling noisy estimates towards a common average.

How far a sample average is likely to be from the truth, σ / √n.

A site served as fixed files with no server-side computation.
