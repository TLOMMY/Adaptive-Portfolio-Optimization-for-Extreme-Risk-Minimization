Time-Travel Portfolio Backend

How the Python pipeline turns ten years of market prices into six model-managed portfolios, and how the demo site replays them in your browser.

Covers: src/portfolio/*.py · model/portfolio.mod · tests/ · site/src/lib/{data,sim,letters}.ts · site/static/data/*.json · written 24 August 2026

How to read this

This page explains the whole backend in one sitting, from the first download of prices to the moment a number appears on the site. It assumes you can read Python but does not assume you know anything about investing or optimisation. Every term is defined the first time it is used, in a box like the one below, and the glossary at the end collects all of them.

Backend

The part of a software project that prepares data and does the computation, as opposed to the part the user looks at. Here the backend is a set of Python scripts that run once, on a laptop, and write files. The site then only reads those files.

Each section makes one main point, gives one example, and sometimes ends with a short question so you can check that the point landed. Where a concept is deeper than this page can go, a grey box lists a good source or a search phrase for YouTube.

The whole picture

The project has two halves that never run at the same time. The Python half downloads prices, builds a mathematical model, and replays ten years of decisions for six imaginary investors. It writes its answers as JSON files into the site's static/data folder. The site half is a static web page that fetches those files and draws them. There is no server, no database, and nothing is computed on demand except the user's own buy-and-hold picks, which are cheap enough to simulate in the browser.

JSON (JavaScript Object Notation)

A plain-text file format for lists and key–value records, for example {"cagr": 0.107, "sharpe": 0.70}. Python writes it with json.dumps and the browser reads it with response.json(), so it is the natural handover format between the two halves.

The order in which things run is fixed. First data.py builds the cleaned price tables. Then tune.py may be run to pick defaults using only 2011–2015. Then export.py runs one backtest per archetype over 2016–2025 and writes the JSON. Finally the site is built. The sections below follow that order, module by module, and then cross into the site.

The words you need first

Four ideas come up in every module, so they are worth fixing before reading any code: a price, a return, a weight, and a portfolio.

Stock, ticker, ETF

A stock (or share) is a small slice of ownership of a company that can be bought and sold on an exchange. A ticker is the short code the exchange uses for it, such as AAPL for Apple. An ETF (Exchange-Traded Fund) is a bundle of many investments that trades like a single stock; this project uses AGG, which holds thousands of US bonds, GLD, which holds gold, and SPY, which holds the 500 largest US companies.

Price and daily return

The price is what one share cost at the close of a trading day. The daily return is the fractional change from one close to the next: if a share closes at $100 on Monday and $102 on Tuesday, Tuesday's return is 102/100 − 1 = 0.02, or 2%. The whole pipeline works in returns rather than prices, because returns can be compared across assets with very different price levels.

Portfolio and weight

A portfolio is the set of everything you hold. A weight is the fraction of your total money in one asset. If you have $10,000 and $1,200 of it is in Apple, Apple's weight is 0.12. Weights across the whole portfolio always add to 1. The optimiser's entire job is to choose weights.

Benchmark and S&P 500

A benchmark is the simple alternative you compare a strategy against. Here it is buying SPY once and never touching it. SPY tracks the S&P 500, an index of roughly the 500 largest US companies weighted by size, which is the usual stand-in for "the US stock market".

One worked example ties these together. Suppose on 4 January 2016 a portfolio holds weights of 0.5 in Apple and 0.5 in cash, and the next day Apple returns −2% while cash returns 0%. The portfolio's return that day is 0.5 × (−0.02) + 0.5 × 0 = −0.01, a 1% loss. That single formula, "portfolio return equals the weighted sum of asset returns", is what both the AMPL model and the backtest loop are built on.

Check yourself. If the portfolio above loses 1% on that day, what are its new weights? (They are no longer 0.5 and 0.5, and that drift is why the backtest has a "drift trigger".)

Running it yourself

The Python side is a package called portfolio living in src/portfolio, managed with uv. The site is a Node project in site/. The only one-off setup step is activating the AMPL licence, which you must do yourself because the licence is personal.

uv

A fast Python package and environment manager. uv run makes sure the virtual environment in .venv matches pyproject.toml and uv.lock, then runs the command inside it, so you never activate an environment by hand.

# one-time: AMPL Community Edition licence (your own UUID)
uv run python -m amplpy.modules activate <uuid>

# 1. download prices and build data/processed/*.parquet (cached in data/raw/)
uv run python -m portfolio.data

# 2. run the tests (needs step 1)
uv run pytest

# 3. optional: hyperparameter grid on 2011-2015 for two profiles
uv run python -m portfolio.tune builder preserver

# 4. backtest every archetype over 2016-2025 and write site/static/data/*.json
uv run python -m portfolio.export          # or: ... export builder sprinter

# 5. the site (Node 22, see site/.nvmrc)
cd site && npm install && npm run dev       # http://localhost:5173
npm run build                              # static output in site/build/

Step 4 takes about two minutes in total; each ten-year profile needs around 25 seconds, of which almost all is the roughly 47 solver calls at about 0.2 seconds each plus the Python loop around them.

The dependencies in pyproject.toml are yfinance and pandas-datareader for downloading, pandas, numpy and pyarrow for tables, amplpy with the ampl-module-base and ampl-module-highs packages for optimisation, and quantstats, which is installed but not used by the current code (the metrics were written by hand in metrics.py so the site could mirror them exactly).

universe.py — what the model may hold

src/portfolio/universe.py

This module is a frozen list, not a computation. It names 51 stocks, two ETFs, and one synthetic cash asset, and records the sector of each. Everything else in the pipeline imports these lists so that "the universe" is defined in exactly one place.

Universe

The set of assets an optimiser is allowed to choose from. A model can only pick from what you give it, so the universe is the first and most consequential design choice.

Sector (GICS)

An industry grouping. GICS (Global Industry Classification Standard) is the scheme used by S&P that puts every listed company into one of about eleven sectors, such as Information Technology or Utilities. Sectors matter here because one of the model's constraints caps how much can sit in any single sector.

The selection rule

The docstring at the top of the file states the rule, applied once by hand and not revised since. A stock had to be in the S&P 500 on 1 January 2016; within each sector the largest companies by market value at the end of 2015 were taken, four to six per sector; and every stock needed a full daily price history back to April 2008, because the tuning period and the three-year estimation window both reach that far back. That last rule excluded Facebook (listed 2012) and LyondellBasell (listed 2010), and Oracle and PPG took their places.

Two extra assets give the optimiser somewhere safe to go when stocks look risky: AGG (a broad US bond ETF) and GLD (gold). A third, CASH, does not exist on any exchange; it is manufactured in data.py from the interest rate on short-term US government debt.

Bond, T-bill, risk-free rate

A bond is a loan to a government or company that pays interest and returns the principal at a fixed date. A T-bill (Treasury bill) is a US government bond that matures within a year; the three-month T-bill is treated by convention as the closest thing to a risk-free investment, and its yield is called the risk-free rate. "Cash" in this project means money parked at that rate, not banknotes in a drawer.

Survivorship bias, disclosed

Companies whose tickers did not survive to 2026 (Dow/DuPont, Monsanto, Praxair and others) were skipped because yfinance cannot return their history. That means the universe is slightly tilted towards companies that turned out fine, which flatters every strategy that draws from it, including the S&P 500 comparison only partly, since SPY itself contains the failures. The file says this plainly and so should any presentation of the results.

Survivorship bias

The distortion that comes from studying only the things that survived. If you test a strategy on the companies that still exist today, you have quietly removed every bankruptcy from the sample.

data.py — fetching and cleaning prices

src/portfolio/data.py

This module downloads daily prices once, caches them, and produces four aligned tables that every later stage reads. Its one rule is that it only stores history; deciding what the model is allowed to see on a given date is somebody else's job (estimate.py).

Downloading

fetch_prices loops over the 53 tickers plus SPY. For each it looks for data/raw/<ticker>.parquet; if the file exists it is read, otherwise yfinance downloads the full history from 1 April 2008 and the file is written. Passing refresh=True forces a re-download. data/raw is git-ignored, so a fresh clone downloads everything on the first run.

Parquet

A compact binary file format for tables, read and written by pandas through pyarrow. It is much faster and smaller than CSV and preserves column types, which is why every table in data/ uses it.

Adjusted close (auto_adjust=True)

Two things break a naive price series. A dividend is cash a company pays to shareholders, and on the day it is paid the price drops by about that amount even though the holder lost nothing. A stock split replaces every share with, say, four shares at a quarter of the price. The adjusted close rewrites past prices so that both effects disappear, and the return series then measures what an investor who reinvested dividends actually earned. yfinance does this when auto_adjust=True.

Manufacturing CASH

fetch_tbill pulls the daily three-month T-bill yield (FRED series DTB3, an annual percentage) and falls back to Yahoo's ^IRX if FRED is unreachable. In build_dataset that annual yield is turned into a daily return and compounded into a price-like series that starts at 1:

daily_rf = (1 + tbill / 100) ** (1 / 252) - 1     # annual % → daily fraction
close["CASH"] = (1 + daily_rf).cumprod()           # a "price" that grows at that rate

The number 252 is the usual count of US trading days in a year and is used for every annualisation in the project. The result is that CASH behaves like any other column: it has a price, it has a daily return, and the model can hold it with a weight.

Alignment and the four outputs

Different tickers occasionally have different trading days in the raw download (a few odd half-days). close.dropna(how="any") keeps only dates where every ticker traded, which removes a handful of rows and guarantees that every table has identical dates. Then the module writes:

File in data/processedShapeMeaning
prices.parquet4,628 days × 55 columnsadjusted close per asset, 2 April 2008 → today, including SPY and CASH
returns.parquetsameprices.pct_change(), the daily return, first row dropped
volume.parquet4,628 × 53dollar volume, price × shares traded, for a liquidity cap that is defined in the model but not currently used by any profile
rf.parquet4,628 × 1the daily risk-free return, used by the Sharpe ratio

load_dataset() reads the four back into a dictionary and is what every other module calls.

estimate.py — what the model is allowed to see

src/portfolio/estimate.py

This tiny module is the honesty gate of the project. Its first function decides which days of history a decision may use, and it always stops strictly before the decision date. The other two functions turn that history into the two inputs the model needs: an expected return per asset and a set of scenarios.

Look-ahead bias

Accidentally letting a simulated decision use information that did not exist yet, for example fitting a model on 2016–2025 and then "testing" it on 2016–2025. It is the single most common way backtests lie, and it is prevented here by construction rather than by care.

window_before

def window_before(returns, t, lookback_days):
    hist = returns.loc[: t - pd.Timedelta(days=1)]   # everything before t, never t itself
    if len(hist) < lookback_days: raise ValueError(...)
    return hist.iloc[-lookback_days:][ASSETS]

Given a date t and a lookback, it returns the last lookback_days rows of returns dated before t. The default lookback is 756 trading days, three years. Because the returns table starts in April 2008, the earliest date this can serve with a 756-day window is April 2011, which is exactly where the tuning period begins.

expected_returns — a shrunk average

The simplest estimate of what an asset will return tomorrow is the average of what it returned over the window. That average is famously noisy: over three years the ranking of assets by sample mean is mostly luck, and an optimiser will happily pile into whatever was lucky. The standard cheap fix is shrinkage: pull every asset's estimate part-way towards the average across all assets.

m = scenarios.mean()                       # sample mean per asset
risky = m.drop("CASH")
out = (1 - shrink) * risky + shrink * risky.mean()
out["CASH"] = m["CASH"]                     # cash is not a noisy estimate; leave it alone

With shrink = 0 each asset keeps its own average; with shrink = 1 every risky asset gets the same expected return and the optimiser can only distinguish them by risk. The tuned value is 0.75. Worked example: if Apple's three-year daily mean is 0.0012 and the cross-asset mean is 0.0004, the shrunk estimate is 0.25 × 0.0012 + 0.75 × 0.0004 = 0.0006.

Lesson learned: never shrink cash

An early version shrank CASH along with the stocks. Cash's true expected return (the T-bill rate, near zero for most of the decade) got pulled up towards the stock average, so the model thought cash paid like a stock without any risk, and sat in cash. Cash's mean is not an estimate at all, it is the known rate, so it is now exempt.

realised_cvar

The third function computes, for a given set of weights, the average loss over the worst 5% of scenario days. It is used after each solve to report what risk the chosen weights actually carry over the window. The idea it implements, CVaR, is important enough to get its own section next.

Measuring risk: VaR and CVaR

Every investor archetype in this project is defined mainly by one number: the largest average loss they will accept on their bad days. That number is a CVaR limit. To read the model you need to understand what CVaR measures and the trick that lets a linear solver compute it.

Scenario

One possible outcome for tomorrow. This project takes each of the last 756 days of history as one scenario, all equally likely: "tomorrow could look like any of these days". The model never assumes a bell curve or any other formula for returns; it just uses the days that happened.

VaR (Value at Risk)

The loss you would exceed only on the worst (1 − α) share of days, for a chosen confidence level α. With α = 0.95 and 756 scenarios, sort the daily losses from worst to best; the 95% VaR is the loss at the boundary of the worst 5%, that is roughly the 38th-worst day. VaR answers "how bad is a bad day?" but says nothing about how bad the days beyond it are.

CVaR (Conditional Value at Risk), also called Expected Shortfall

The average loss over those worst 5% of days. It is always at least the VaR, and it does account for how deep the tail goes. A daily 95% CVaR of 2% means "on your 5% worst days you lose 2% on average". As a rough feel, a portfolio with a daily CVaR of 2% loses about 8–10% in a bad month.

A miniature example with twenty scenarios and α = 0.95 makes the difference concrete. The worst 5% of twenty days is one day. Suppose the two worst daily losses are 6% and 3%. The VaR is the boundary of the worst 5%, so it is about 6% (with one day in the tail, VaR and CVaR coincide). Now suppose there were forty days, so the tail holds two days: VaR is 3% (the boundary), and CVaR is the average of 6% and 3%, which is 4.5%. CVaR noticed the 6% day; VaR did not.

The Rockafellar–Uryasev trick

Computing "the average of the worst 5%" seems to need sorting, which is not something a linear program can do. Rockafellar and Uryasev (2000) showed that CVaR is the minimum over a free number ζ (zeta) of the following expression, where L_s is the portfolio loss in scenario s and [x]⁺ means "x if positive, else 0":

CVaR_α = min over ζ of: ζ + (1 / ((1 − α) · nS)) · Σ_s [L_s − ζ]⁺

The intuition is that ζ is a threshold you are guessing, and you pay for every scenario whose loss overshoots it, scaled up by 1/(1 − α) so that overshoots count 20 times. The expression is smallest exactly when ζ equals the VaR, and at that point its value equals the CVaR. In a model you replace [L_s − ζ]⁺ with a new non-negative variable u_s and a constraint u_s ≥ L_s − ζ; because the objective pushes every u_s as low as it can go, the two are equivalent and everything stays linear. That is precisely what portfolio.mod does with its zeta, u[s], and tail_loss constraint.

Linear program (LP)

An optimisation problem in which the objective and every constraint are straight-line (linear) functions of the decision variables. LPs with hundreds of thousands of variables solve in seconds with standard software, which is why a linearisable risk measure like CVaR is so useful.

Check yourself. In the twenty-scenario example, if you set ζ far below every loss, does the Rockafellar–Uryasev expression get bigger or smaller than the true CVaR, and why?

model/portfolio.mod — the optimisation model

model/portfolio.mod (39 lines of AMPL)

This file is the heart of the project. It describes one decision: given estimates and an investor's rules, which weights to hold until the next rebalance. It is written in AMPL, solved by HiGHS, and called once per rebalance date from Python.

AMPL and HiGHS

AMPL (A Mathematical Programming Language) is a language for writing optimisation models in something close to mathematical notation, separately from the data. A solver is the program that actually finds the best solution; HiGHS is a free, open-source solver for linear and mixed-integer problems, and amplpy is the Python library that loads a model, fills in its data, and calls the solver.

MILP (Mixed-Integer Linear Program)

A linear program in which some variables must be whole numbers, here 0 or 1. Integer variables let a model express yes/no decisions ("do I hold this asset at all?"), at the cost of making the problem much harder in theory. In practice, this one has 53 binaries and HiGHS solves it in a fifth of a second.

Sets and parameters

AMPL separates the shape of a problem (sets) from its numbers (parameters, "params"). Python fills all of these in before each solve.

Basis point (bp)

One hundredth of one percent. A 10 bp cost means paying $1 for every $1,000 traded, a reasonable all-in figure for large US stocks including the gap between buying and selling prices.

Decision variables

var w    {a in ASSETS} >= 0, <= w_max[a];   # the weights: the actual decision
var z    {ASSETS} binary;                   # 1 if the asset is held at all
var buy  {ASSETS} >= 0;                     # how much weight is bought ...
var sell {ASSETS} >= 0;                     # ... and sold, relative to w_prev
var zeta;                                   # the VaR threshold from the R-U trick
var u    {SCENARIOS} >= 0;                  # loss beyond zeta in each scenario

Three named expressions are defined for readability. cvar is the Rockafellar–Uryasev formula zeta + Σ u[s] / ((1 − alpha) · nS). exp_return is Σ mu[a] · w[a], the expected daily portfolio return. turnover is Σ (buy[a] + sell[a]), the total weight that changes hands.

The objective

maximize hold_days · exp_return − lambda_risk · cvar − cost_rate · turnover

The model wants the highest expected return over the holding period, minus what it costs to get there. Risk is handled mostly as a hard limit (below), so lambda_risk is zero for every profile and the middle term is dormant; it exists so a profile could trade return for risk smoothly instead of with a cliff.

Lesson learned: scale return by hold_days

The first version maximised exp_return − cost_rate · turnover. Expected return is a daily number, around 0.0005, while switching a 10% position costs 0.001 × 0.2 = 0.0002 once. One day of return could never justify a trade, so the model sat in cash and never rebalanced. Multiplying the return by the 21 days the position is expected to be held compares like with like, and the model started trading sensibly.

The constraints

Each constraint below is one rule an adviser might state in words. Reading them in this order tells the story of the model.

ConstraintIn AMPLIn words
budgetΣ w[a] = 1All the money is placed somewhere; cash counts as somewhere.
trade_balancew[a] = w_prev[a] + buy[a] − sell[a]The new weight is the old weight plus what was bought minus what was sold. Because both buy and sell are non-negative and cost money, the solver never sets both positive for one asset.
tail_lossu[s] ≥ −Σ r[s,a]·w[a] − zetaIn each scenario, u[s] must cover the portfolio loss beyond the threshold. The portfolio loss is minus the portfolio return, hence the leading minus sign.
loss_tolerancecvar ≤ cvar_limitThe average loss on the worst 5% of scenario days may not exceed the investor's limit. This is the constraint that defines each archetype.
link_upperw[a] ≤ w_max[a] · z[a] (non-cash)If z[a] is 0 the weight must be 0; if it is 1 the weight may go up to the cap. This links the continuous weight to the yes/no variable.
link_lowerw[a] ≥ w_min_pos · z[a] (non-cash)If the asset is held, hold at least 2%. This stops "dust" positions of 0.01% that would be pointless to trade.
cardinalityΣ z[a] ≤ max_holdings (non-cash)No more than this many different assets. This is the rule that needs the binaries and makes the problem a MILP.
sector_limitΣ w[a] over sector k ≤ sector_cap[k]No sector gets more than its cap; the default cap is 1.0 (no limit) unless a profile sets one.
cash_floorw[CASH] ≥ cash_minKeep at least this much liquid.

Cardinality constraint

A limit on how many things are chosen, as opposed to how much. "Hold at most twelve stocks" is a cardinality constraint. It cannot be written with weights alone, because a weight of 0.0001 would still count as not holding, so a binary indicator per asset is needed.

Worked example of the link constraints: with w_max = 0.12 and w_min_pos = 0.02, asset a may have weight 0 (with z = 0) or any weight in [0.02, 0.12] (with z = 1), but nothing in between 0 and 0.02. The binaries make the feasible region disconnected, which is exactly what a plain LP cannot represent.

Check yourself. If a profile sets max_holdings = 8 and w_max = 0.20, what is the most that can be in stocks and ETFs combined, and where must the rest go?

optimiser.py — calling the model from Python

src/portfolio/optimiser.py

This module does one thing: take pandas objects in, hand them to AMPL, and return a Solution. It knows nothing about dates, so it cannot possibly leak future information; the only way to get scenarios into it is through estimate.window_before.

One AMPL session, reused

_get_ampl() creates a single AMPL object the first time it is called and keeps it in a module-level variable. Creating the session is slow (it starts a separate process); reusing it means each solve pays only for loading data. Three options are set once: the solver is highs, all solver chatter is silenced, and HiGHS is told mip_rel_gap=1e-4 timelim=60.

MIP gap

A solver proves a mixed-integer solution is optimal by squeezing an upper bound and the best solution found towards each other. The relative gap is how far apart they still are; stopping at 0.01% means the returned answer is within 0.01% of the best possible, which is far below the noise in the inputs.

The solve function, step by step

  1. Build the asset list from mu.index and the sector list from those assets. If no previous weights are given, assume 100% cash.

  2. Turn w_max into a per-asset Series if a single number was given, force CASH's cap to 1.0 (cash is always allowed in any amount), and set the cap to 0 for any ticker in the profile's exclude list, which is how the Ethical Investor refuses Philip Morris.

  3. ampl.reset() then ampl.read(MODEL) reloads the model file fresh, so nothing from the previous solve leaks through.

  4. Fill every set and parameter. The biggest is r, a dictionary of 756 × 54 ≈ 41,000 entries keyed by (scenario, asset), built with one comprehension over the NumPy array.

  5. ampl.solve(), timed. If the result is anything other than "solved" (for example "infeasible" when no portfolio can meet a very tight CVaR limit and a cash floor at once) a RuntimeError stops the backtest rather than silently continuing.

  6. Read w back, zero anything below 10⁻⁶, and package it with the model's expected return, the turnover, and the CVaR of those weights recomputed in Python by realised_cvar. Recomputing rather than reading the model's cvar variable is a small cross-check that the linearisation did what it claims.

@dataclass
class Solution:
    weights: pd.Series      # the answer, one weight per asset
    exp_return: float       # expected daily return, mu · w
    cvar: float             # realised CVaR of these weights over the scenarios
    turnover: float         # Σ |trades| as a fraction of portfolio value
    status: str             # "solved"
    solve_time: float       # seconds inside ampl.solve()
    n_holdings: int         # non-cash assets with positive weight

profiles.py — six investors as numbers

src/portfolio/profiles.py

A Profile holds what a person would tell an adviser: how long the money is for, how much loss they can stomach, how many holdings they want, and any exclusions. params_at(years_left) translates that into the parameter dictionary the model needs on a given date. Only one thing changes with time: the loss limit.

The glide path

Horizon and glide path

The horizon is how many years until the investor needs the money. A glide path is a rule that makes a portfolio safer as the horizon shrinks, the idea behind "target-date" retirement funds. Here it is a straight line on the CVaR limit:

cvar_limit(years_left) = cvar_end + (years_left / horizon_years) · (cvar_start − cvar_end)

For The Builder, cvar_start = 0.020 and cvar_end = 0.010 over ten years, so at the start the model may run a 2.0% daily CVaR, five years in it may run 1.5%, and in the final months only 1.0%. The fraction is clamped to [0, 1] so nothing strange happens if a backtest runs past the horizon. This is the project's first "policy" idea: the risk budget is a state that depends on time, not a constant.

backtest.py — replaying ten years honestly

src/portfolio/backtest.py

A backtest replays a strategy day by day over history as if it had been run live. This one walks forward through every trading day from 4 January 2016, lets the portfolio earn that day's returns, decides whether to re-solve, and if so trades at that day's close using only history before that day. The whole module is one loop and the honesty lives in its ordering.

Walk-forward backtest

A simulation that moves through time in order, making each decision with only the data that was available at that moment, then revealing the next day and repeating. It is the opposite of fitting one model to the whole period at once.

Rebalance

Trading a portfolio back to a chosen set of weights. Weights drift on their own as prices move, so any strategy that targets weights has to decide when to rebalance and pay the trading costs of doing so.

One day in the loop

Let holdings be a Series of dollar amounts per asset, starting as all cash. For each trading day t:

  1. Earn. Except on the very first day, multiply each holding by 1 + returns.loc[t]. Compute the new total and the current weights w = holdings / total.

  2. Decide whether to re-solve. A reason is set if any trigger fires (next subsection). On the first day the reason is "start".

  3. Re-solve, if needed. Compute years_left to the horizon end. Take the 756-day window before t, shrink its means, ask the profile for its parameters at this years_left, and call solve with the current weights as w_prev.

  4. Trade and pay. The new dollar holdings are sol.weights × total. The amount traded is the sum of absolute dollar changes; the cost is cost_rate times that; and the cost is taken out of every position pro rata by scaling all holdings by 1 − cost/total. Every asset whose weight changed by more than 0.01 percentage points is logged as a trade, and one row is logged for the solve itself.

  5. Record. Append today's total value and weights.

The new weights earn returns only from t + 1. So the model never earns a return on the same day's data it was allowed to see, and the scenarios it saw ended the day before t. Worked example from the exported Builder run: on 4 January 2016 the first solve moved 98% of $100,000 out of cash into nine holdings, so turnover was 1.96 (buys plus sells), the cost was 0.001 × 1.96 × 100,000 = $196, and the recorded value on day one is $99,804. That is why the site's adviser line starts a hair below the S&P line.

The triggers

This is the project's second "policy" idea: rebalancing is event-driven rather than on a fixed calendar. After a cooldown of min_days_between (10 trading days, so a crash cannot cause a solve every day), the loop checks three conditions in this order and uses the first that fires:

ReasonConditionWhy it exists
calendar63 trading days (one quarter) since the last solveA floor on attention: even a quiet market gets a review each quarter and the glide path keeps tightening.
driftΣ |w − target| ≥ 0.10, where target is the last solved weightsPrices have pulled the portfolio 10 percentage points in total away from what was chosen.
volatility21-day volatility of the equal-weight universe ÷ its 252-day volatility ≥ 2.0The market has become twice as jumpy as usual, so the risk the old weights carry has changed even if the weights have not.

Volatility

The standard deviation of returns, that is how widely they scatter around their average. High volatility means big moves in both directions. market_vol_ratio computes it over the last 21 and 252 trading days on the average return of all 53 tickers, again using only data before t.

In the exported Builder run there were 49 solves: 1 start, 34 calendar, 5 drift, and 9 volatility. The volatility trigger fired around events such as February 2018, March 2020 and April 2025, which is what it is for.

The benchmark and the horizon

The benchmark is SPY bought once with the same initial amount; its series is normalised so that day one equals initial, matching the portfolio's day one, on which no return is earned. The end date is the earlier of the requested end and start + horizon_years, so The Sprinter's backtest runs only three years, to 4 January 2019, with 757 days instead of 2,514, and its benchmark metrics cover the same three years.

The function returns a BacktestResult with the daily value series, daily weights, the benchmark series, the solve log, the trade log, and the metrics of both portfolio and benchmark.

tune.py — choosing defaults without peeking

src/portfolio/tune.py

Four settings are not part of any investor's story but still affect results: the lookback window, the shrinkage, the drift trigger and the volatility trigger. They are hyperparameters, and choosing them by trying values on 2016–2025 would be look-ahead bias in another disguise. So tune.py tries them on 1 April 2011 to 31 December 2015, a period the site never shows.

Hyperparameter

A setting of the method itself rather than a quantity the method estimates. The model estimates expected returns; how many days of history to estimate them from is a hyperparameter.

The grid and the selection rule

GRID = {
    "lookback_days": [504, 756],          # two or three years of scenarios
    "shrink":        [0.5, 0.75, 1.0],
    "drift_trigger": [0.10, 0.20],
    "vol_trigger":   [1.5, 2.0, 99.0],    # 99 = volatility trigger effectively off
}

That is 36 combinations, run for The Builder and The Preserver, so 72 backtests in a process pool of four. For each run it records CAGR, Sharpe, maximum drawdown, realised CVaR, the profile's average CVaR limit over the run, their ratio, and total turnover. The selection rule is stated in the docstring: keep configurations whose realised CVaR stayed within 10% of the average limit (the risk promise was kept), then take the highest Sharpe, with ties going to the one that traded least.

What it found, and what was actually chosen

The per-profile winners disagreed on shrinkage and drift (Builder's best was shrink 0.5 and drift 0.2; Preserver's was shrink 0.75, drift 0.1, and no volatility trigger). Rather than give each profile its own tuned settings, which would overfit two small samples, the defaults in profiles.py were set from the marginal means of Sharpe across all 72 runs, that is the average Sharpe of every run that used a given value:

SettingMean Sharpe by valueChosen default
lookback_days504: 1.009 · 756: 1.130756
shrink0.5: 1.029 · 0.75: 1.093 · 1.0: 1.0870.75
drift_trigger0.10: 1.080 · 0.20: 1.0590.10
vol_trigger1.5: 1.063 · 2.0: 1.082 · off: 1.0642.0

The full table of 72 rows is in data/processed/tuning.json and the console summary in tuning.log. The differences are small, which is itself the finding: on 2011–2015 the strategy is not very sensitive to these settings, and the longer window helps most.

export.py — the handover to the site

src/portfolio/export.py

This is the last Python step and the only one that writes into site/. It runs one full backtest per profile over 4 January 2016 to 31 December 2025 and writes five kinds of JSON into site/static/data. Every number is rounded (four decimals for weights, two for dollars, six for metrics) to keep the files small enough to fetch comfortably.

universe.json (6 KB)

{ "assets": [ {"ticker": "AAPL", "name": "Apple", "sector": "Information Technology", "kind": "stock"}, …,
              {"ticker": "AGG", …, "kind": "etf"}, {"ticker": "CASH", "name": "Cash (T-bills)", "sector": "Cash", "kind": "cash"} ],
  "benchmark": "SPY", "start": "2016-01-04", "end": "2025-12-31" }

Fifty-four entries in universe order. kind is derived from the sector: Bonds and Gold are etf, CASH is cash, everything else is stock. The site uses this to lay out the stock-picking cards by sector and to group weights into stocks, bonds and gold, and cash.

prices.json (1.1 MB)

{ "dates":  ["2016-01-04", …, "2025-12-31"],          # 2,514 trading days
  "assets": ["AAPL", …, "GLD", "SPY", "CASH"],         # 55 columns

Every column is divided by its first value, so each series starts at exactly 1.0 and a value of 2.5 means "$1 became $2.50". This normalisation is what lets the browser price any buy-and-hold portfolio by multiplication alone. It is also the only file the timeline stage uses.

Two size decisions are worth knowing. Weights are resampled to one row per week (the last value up to each Friday) rather than daily, because the ribbon chart cannot show more detail than that and daily weights would triple the file. And the weight columns include only assets that were ever held, so The Maverick's file has fewer columns than The Preserver's. index.json is just the six profile blocks in one list, so the archive page can show the adviser cards without loading six large files.

summary.json (2 KB)

One row per profile with the headline metrics next to SPY's over the same dates. It is written for reporting and for this documentation; no site component currently reads it. The main loop merges into any existing file, so exporting a single profile (… export sprinter) updates only that row.

The tests

tests/test_data.py · tests/test_optimiser.py

The tests are few and pointed. They need the processed data to exist and a working AMPL licence, so they are integration tests rather than unit tests.

  • test_dataset_shape_and_coverage: the price table has exactly the 55 expected columns, starts by 2 April 2008, reaches past 1 January 2026, and contains no missing values; the returns table has the same dates.

  • test_cash_is_smooth_and_positive: the CASH return is never below −0.001% (T-bill yields dipped slightly negative in March 2020) and never above 0.1% in a day. This guards the synthetic asset against a bad download.

  • test_no_lookahead: the window before 4 January 2016 has 756 rows and its last date is before 4 January 2016.

  • test_solution_respects_constraints: with a 1.5% CVaR limit, the solved weights sum to 1, no asset exceeds its 10% cap, every held asset is at least 2%, at most 15 are held, and the realised CVaR is within the limit.

  • test_tighter_limit_means_less_risk_and_return: a 1.0% limit produces no more CVaR and no more expected return than a 2.0% limit. This checks the economic direction of the model, not just its feasibility.

Into the site

Everything from here on happens in the browser. The site is written in SvelteKit with hand-written CSS and D3 for the two charts. This section follows the same data through the site that the earlier sections produced, so you can trace any number on screen back to a line of Python.

SvelteKit, Svelte 5 runes

Svelte is a framework for building web interfaces from components, files that mix HTML, JavaScript and CSS. SvelteKit adds routing and building around it. Svelte 5 introduced runes, functions like $state and $derived that mark which values are reactive, meaning the page redraws automatically when they change.

A site with no server

vite.config.ts uses adapter-static and +layout.ts sets prerender = true. That means npm run build produces a folder of plain HTML, JavaScript and JSON in site/build that any file host can serve; there is no code running on a server after deployment. Everything in site/static, including data/, is copied into the build unchanged, so a URL like /data/profiles/builder.json simply returns the file export.py wrote. Deployment is a push to GitHub that Vercel builds and hosts.

Static site

A website whose files are fixed at build time and served as-is. It cannot compute anything per visitor on the server, which is exactly why the heavy work was precomputed in Python. The trade-off is that a user cannot ask for a new archetype; only the six that were exported exist.

data.ts — loading and typing the JSON

site/src/lib/data.ts

This file declares a TypeScript interface for each JSON file (Universe, Prices, ProfileResult, Solve, Trade, Metrics, ProfileMeta, MarketEvent), and every field name in them matches the Python dictionary keys exactly. If a key is renamed in export.py, the type here must change too; there is no runtime check.

const cache = new Map<string, Promise<unknown>>();
async function getJson<T>(path: string): Promise<T> {
  if (!cache.has(path)) {
    cache.set(path, fetch(`${base}/data/${path}`).then((r) => {
      if (!r.ok) throw new Error(`failed to load ${path}: ${r.status}`);
      return r.json();
    }));
  }
  return cache.get(path) as Promise<T>;
}
export const loadUniverse = () => getJson<Universe>('universe.json');
export const loadPrices   = () => getJson<Prices>('prices.json');
export const loadProfile  = (key) => getJson<ProfileResult>(`profiles/${key}.json`);

The cache stores the promise, not the result, so two components asking for the same file at the same moment share one network request. base is SvelteKit's base path, empty on Vercel, so the fetch goes to /data/….

Global state lives in state.svelte.ts as one reactive object: the current stage, the wished-for amount, the user's allocations (ticker → dollars), the chosen adviser key, and a cursor into the date array. +page.svelte shows one component per stage and, on load, fetches universe.json, prices.json and events.json in parallel.

Journey is where the two halves meet. It loads the chosen profile's file, then builds three value series of equal length n:

const scale   = app.amount / 100_000;
const you     = buyAndHold(prices, app.allocations, app.amount).slice(0, n);   // computed here
const adviser = result.value.map((v) => v * scale);                            // from Python

The adviser's series is the Python value array scaled by amount / 100,000. That is legitimate because the whole model works in weights and every cost is proportional, so a $10,000 investor gets exactly one tenth of the $100,000 path. (The one place this breaks down is in reality, not the model: a $100 investor cannot buy 2% of Apple.) The cursor advances a few trading days per animation frame, the D3 line chart draws the three series up to the cursor, the weights ribbon draws the weekly weights up to the cursor date grouped by sector, and the two side panels show the latest "letter" and the latest world event at or before the cursor date.

Debrief puts the eight metrics side by side. The adviser's column is the Python metrics block with only start_value and end_value rescaled (ratios do not change with scale). The "You" and "S&P 500" columns are computed in the browser by sim.ts. The line under the table sums cost over the solve log and scales it.

sim.ts — the browser's copy of the maths

site/src/lib/sim.ts

buyAndHold(prices, dollars, total) prices the user's picks on every day as Σ dollars[t] × normalised price[t] plus leftover cash growing with the CASH column. Because prices are normalised to 1.0 on day one, "$1,200 in Apple" is simply 1200 × row[AAPL]. There are no trading costs on the user's side, on the argument that one purchase in 2016 is negligible against ten years.

summarise(dates, value, rf) is a line-by-line port of metrics.py: same 252-day annualisation, same sample standard deviation (dividing by n − 1, matching pandas), same running-maximum drawdown, same month-end detection (a day is a month end if the next date's year-month differs), same "largest 5% of losses" CVaR. riskFree(prices) derives the daily risk-free return from the CASH column, which is the same number rf.parquet holds because CASH was built from it. If you change a formula in metrics.py, change it here too.

letters.ts — turning the solve log into prose

site/src/lib/letters.ts

Each row of solves becomes a short letter from the adviser. The opening sentence is chosen by the reason field (start, calendar, drift, volatility). The trades logged on that date are grouped, the three largest increases and decreases are named using the company names from universe.json, and a running target map (updated trade by trade) gives the split between stocks, bonds and gold, and cash for the first letter. Each letter then states the day's cvar_limit in words and, if the horizon has started to bite, says that it tightens as the years left shrink. The trading cost of that solve closes the letter. The Journey page can read letters aloud with the browser's speech engine.

Rebuilding after a change

Because the two halves communicate only through files, the update path is always the same three steps, and skipping one is the usual cause of "the site shows old numbers":

  1. Change the Python (a profile number, a constraint, a trigger) and run uv run python -m portfolio.export, or … export <key> for one profile. This overwrites the JSON in site/static/data.

  2. If a JSON key was added or renamed, update the matching interface in data.ts and whichever component uses it.

  3. Run npm run build in site/ (or let Vercel do it on push). The dev server on port 5173 picks up new static files without a rebuild; the preview server on 4173 does not.

What this does not do

A reader should leave knowing the edges as well as the mechanism.

  • Survivorship bias in the universe. Companies that disappeared before 2026 are missing, as described under universe.py.

  • Hand-picked archetype numbers. The six profiles' limits and caps are illustrative until the planned calibration from cited sources is done.

  • Scenarios are the past. The CVaR limit is enforced over the last three years of history, so a future that is worse than anything in the window will exceed the limit. The realised CVaRs above show the size of that gap.

  • No taxes, no dividends withheld, no slippage beyond 10 bp. Returns are total returns (dividends reinvested), costs are a flat proportional rate, and every trade fills at the closing price.

  • Liquidity cap is unused. volume.parquet and the per-asset w_max mechanism exist so that a profile could cap positions by dollar volume, but no profile does.

  • The site cannot run new profiles. Only exported archetypes exist; a custom risk limit would need a Python run and a redeploy.

  • The sentiment idea is not built. The stretch goal of feeding news sentiment into expected returns via Black–Litterman has no code yet.
